# 04: 实现双运行时的上下文观测与自动 worker 交接

**What to build:** 小工具观测 Pi／OpenCode worker 的上下文，在达到阈值或收到主动交接指令时，自动让旧会话生成 handoff 文档，并用同一工单的新会话继续工作。正常交接无需主脑介入，异常可由主脑处置。

**Blocked by:** 03 — 让 OpenCode 使用同一套单工单执行接口。

**Status:** delivered（执行记录与证据：[../evidence/04-worker-context-handoff/README.md](../evidence/04-worker-context-handoff/README.md)；待主脑确认集成）

> 执行中发现 Pi 会话模型注册表不返回 context window（E04，已在本工单修复）；阈值低于新会话起始上下文会连续交接（E05，观察项）；E02／E03 仍待主脑汇总到共享 README。详见证据 README 第 6 节。

## 依据与边界

依据：[项目重建方案](../项目重建方案.md)第 5、6、8、10 节。

本工单处理单 worker 跨会话续接，不实现主脑交接、崩溃接管或自动业务重试。交接仍属于同一个 worker 和工单，不另占业务执行槽。

## 验收条件

- [x] Pi、OpenCode 均能读取可解释的当前上下文观测值，区分累计消耗、有效调用、陈旧样本及不可观测情况；无法观测不按零用量处理。
- [x] 默认达到 300K tokens 或窗口占用 80% 触发，阈值可配置；主动交接使用同一条标准流程。
- [x] 触发后暂停旧业务执行与等待，确认可交互，使用已验证的方式调用 handoff skill；交接材料包含进展、决定、验证、提交、未提交内容和下一步。
- [x] 在替换前确认文档可读并保存到耐久管理位置；结构缺失时允许有限补正，不能只靠字数判定交接充分。
- [x] 新对话收到原工单合同和交接文档，保持相同 worktree、branch、provider、model、thinking，并实际读取材料继续未完任务。
- [x] 旧会话停止业务写入后新会话才开始工作；新会话启动与投递确认后结束旧会话，不允许两个会话同时修改同一 worktree。
- [x] 会话序号递增，观测、等待及异常关联具体会话；旧采样与旧事件不会触发新会话的重复交接，连续多次交接仍属于同一工单执行。
- [x] 文档生成、观测或替换启动失败形成可读取的待处理异常，保留文档、分支和工作现场；成功交接只记录进展，不要求主脑作决定。
- [x] 使用可控低阈值分别完成 Pi、OpenCode 的真实续接演示；用确定性模拟验证陈旧事件、替换失败、停止与交接竞争等边界。

## 验证重点

覆盖验收场景 3、4，以及场景 11 中同一 worker 不因交接产生并行业务写入的要求。
