# 02: 跑通 Pi 单工单的启动、执行与成果交付

**What to build:** 主脑通过新工具启动一个隔离的 Pi worker，提供明确的工单材料和运行配置。工具在后台监督该工单，主脑能够查看执行事实、读取交付或异常，并停止 worker、保留现场。

**Blocked by:** 01 — 验证 Herdr 与双运行时的最小执行链路。

**Status:** ready-for-agent

## 依据与边界

依据：[项目重建方案](../项目重建方案.md)第 3、5、6、7、10 节及实施阶段二。

建立新入口与最小单 worker 路径，按需提炼旧实现的可靠能力。此时不引入自动交接、全局排程或完整旧接口兼容层；暂不删除旧执行器。接口边界应允许随后接入 OpenCode、上下文观测与多 worker 等待。

## 验收条件

- [ ] 主脑可用工单标识、明确任务材料、确认的 Pi 配置、仓库和完整 base SHA 发起单工单执行；缺失或无效配置在业务投递前明确失败。
- [ ] 从指定基线创建独立分支与 worktree，登记 worker、工单、运行配置、Herdr 定位、监督身份和结果位置；不复用归属不明资源。
- [ ] Worker 能读取主 checkout 中未提交或被忽略的 spec／工单材料；使用可访问引用或受控快照并保留来源，不假定 Git worktree 自动携带这些文件。
- [ ] 投递合同明确单工单范围、验收要求、材料、工作目录、结果位置及阻塞报告方式；worker 不修改主脑的计划和其他工单文件。
- [ ] 启动调用返回后监督仍可运行，查看操作返回启动、运行、交付、失败或待决策等事实；监督缺失可见，不伪装为正常运行。
- [ ] 交付结果关联工单和 worker，含完成摘要、验收及实际验证结果、分支／HEAD 或非代码产物、遗留问题；工具只检查协议和资源一致性，不代替质量验收。
- [ ] 代码工单与调查／验证工单均能交付；后者不强制生成空提交。终端 idle/done 而无有效结果不能标记交付。
- [ ] 对明确瞬态启动／投递错误作有限机械重试；投递是否接受不确定时先观察，不盲目重发。缺失结果允许一次补报，仍无效则形成协议异常。
- [ ] 停止操作结束业务执行和监督，保留结果、分支及 worktree；交付和失败都不自动强制删除现场，不设置工单执行时间或费用预算。
- [ ] 提供可重复的单工单使用步骤，以及覆盖正常交付、非代码交付、材料可见性、结果缺失、错误分支／HEAD 和停止保留的有意义验证。

## 验证重点

覆盖验收场景 6 的完成语义、场景 10 的材料可见性、场景 12 的非代码交付，并奠定场景 9 的保留现场行为。
