# 03: 让 OpenCode 使用同一套单工单执行接口

**What to build:** 主脑通过与 Pi 相同的操作选择 OpenCode worker，并完成隔离启动、后台执行、状态查看、成果交付及停止。运行时差异封装在适配边界内。

**Blocked by:** 02 — 跑通 Pi 单工单的启动、执行与成果交付。

**Status:** ready-for-agent

## 依据与边界

依据：[项目重建方案](../项目重建方案.md)第 5、6、7 节，以及 01 的真实链路验证结论。

复用已有工单与结果语义，不另造一套 OpenCode 状态模型或排程器。第一版仍只支持 Pi 和 OpenCode，不接入 Codex。

## 验收条件

- [ ] 同一启动、查看和停止接口支持选择 Pi 或 OpenCode，除必要运行时配置外，不要求主脑学习不同执行流程。
- [ ] OpenCode 显式接受并保存 provider、model、thinking；校验模型与推理配置的兼容性，不使用未确认的默认模型或静默替换。
- [ ] 采用 01 验证过的模型和推理配置映射方式，并提供实际生效证据；不能将根 TUI 不支持的参数从其他子命令直接照搬。
- [ ] 配置注入不修改业务仓库中受跟踪或本地的配置文件，也不覆盖已有权限设置；交接所需固定配置可被后续适配使用。
- [ ] 正确处理 OpenCode 的就绪、投递、中断和错误／blocked 信号；错误不被误报为成果交付。
- [ ] OpenCode 交付遵循相同的工单、worker、branch／HEAD 或产物关联检查；代码与非代码任务均可用。
- [ ] 停止保留及未知投递状态的处理与 Pi 保持相同语义，不自动销毁成果或重复业务请求。
- [ ] 提供一组双运行时契约验证和 OpenCode 实际冒烟证据，已有 Pi 单工单链路继续通过。

## 验证重点

完成验收场景 1 的双运行时工具行为，并将场景 6、10、12 的既有单工单语义延伸到 OpenCode。
