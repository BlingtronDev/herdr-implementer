# 07: 交付主脑动态管理计划的 skill

**What to build:** 提供可实际使用的计划执行管理 skill，使主脑读取完整初始工单集、一次确认授权、动态派发、处理待处理事项、执行正常合并并维护简洁执行记录。主脑可以自主调整工单，不受固定批次限制。

**Blocked by:** 05 — 实现多 worker 并发与待处理事项等待；06 — 实现交付保留与按决定清理。

**Status:** ready-for-agent

> 接口现状（工单 05 已集成：`0ee66d7`）：并发与等待由 `bin/plan_manager.py` 的 `init-run`／`start --run`／`status --run`／`wait`／`ack` 提供，本工单的操作说明以此为准。一次确认写入 run（运行配置 + `max_workers`）；`wait` 默认无限等待，`--timeout` 只限制窗口且超时无结论；`ack` 输入 `<worker-id>/<item-id>`，不代表集成；`--handoff-tokens` 应高于新会话种子上下文（E05）。见 [README E07](README.md)。

> 接口现状（工单 06 已集成：`3a60d48`）：`stop` 确认全部登记会话停止业务写入并在交接竞争中暂停替换会话，响应含 `business_stopped`；worker 写出结果后不再自动交接。清理使用 `cleanup --worker <id> (--integrated <sha> | --disposition <text>) [--archive-uncommitted | --discard-uncommitted] [--delete-branch [--force-branch]]`，默认保留分支、只关闭登记 tab、未提交内容默认保留；`status --worker` 的 `cleanup` 字段可查询资源位置与未清理原因。见 [README E08](README.md)。

## 依据与边界

依据：[项目重建方案](../项目重建方案.md)第 1、3、4、5、6、7 节。

编写或修改 skill 时使用适用的 agent 文档编写规范。新工作流可通过预览入口验证，最终名称切换和旧入口删除留给迁移工单。冲突及整体收口在此明确职责，完整修复场景由 08 补齐。

## 验收条件

- [ ] 启动要求 spec／计划和完整初始工单集，支持默认本地约定和用户指定路径；主脑理解语义依赖，工具不引入严格 Markdown 工单解析和全量 DAG 排程。
- [ ] 一次确认目标、范围、kind、provider、model、thinking 及最大并发数；只询问缺失或矛盾信息，不要求四轮固定问答，不设置任务时间或费用预算。
- [ ] 主脑在授权内决定执行顺序、并行组合、常规失败处置和工单新增／拆分／调整，记录简要原因；不可推断的需求取舍或授权变化才询问用户。
- [ ] 主脑能组合使用启动、查看、等待、确认处理、停止和清理操作，成功自动交接无需主脑确认；双运行时交接与多 worker 等待组合工作正常。
- [ ] 执行记录明确区分成果交付与成果集成，包含相关工单和集成 SHA；ack 不被当作集成，依赖工单只在所需成果已集成后启动。
- [ ] 主脑直接执行符合仓库规范的正常合并，保留按需复核权；遇到具体修复问题派 worker，不亲自修改业务代码。
- [ ] 在 A、B 并行且 C 只依赖 A 的演示中，A 集成后 C 可在 B 结束前启动，整个过程不突破并发额度。
- [ ] 使用说明与 worker 合同足够独立可用，具体操作参考按需加载；主脑不用记忆运行时按键和后台启动细节。
- [ ] 正常执行不依赖主脑交接、崩溃恢复、固定批次计划或隐藏的后台领单逻辑。

## 验证重点

覆盖验收场景 2、6、11 的主脑行为，并完成自动交接、并发、等待和保留现场的首次组合验证。
