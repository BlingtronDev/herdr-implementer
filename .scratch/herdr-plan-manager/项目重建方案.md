# Herdr Plan Manager 项目重建方案

本文记录本次设计讨论达成的共识，以及据此提出的实现方案。目标名称为 `herdr-plan-manager`，替代现有 `herdr-ticket-dispatcher`。本文是建设方案，不表示新工具已经实现或验证。

## 1. 目标与核心判断

利用 Herdr 启动独立的 Pi／OpenCode worker，由主脑组织它们落实用户确认的 spec 或计划。单个 worker 负责一个工单，必要时通过 handoff 更换会话继续执行。

核心原则：**主脑负责判断，worker 负责具体工作，工具负责机械可靠性。**

现有项目的主要问题不是自动化太多，而是自动化和职责边界不匹配：固定批次、固定问答顺序、重复确认等规定限制了主脑；终端控制、上下文交接、任务状态和排程政策又集中在同一个执行器中。

采用按新职责边界重建、复用经过验证的底层能力的路线。新项目应是 spec／计划的执行管理 skill，而不是另一个自动排程服务。

### 1.1 已确认的范围

- 输入必须包含 spec／计划及完整初始工单集。
- 用户一次确认目标与授权边界，主脑动态决定执行安排。
- 主脑可以在授权范围内新增、拆分和调整工单，并记录原因。
- 主脑自主处理常规失败；无法推断的需求取舍、扩大目标或改变授权约束时询问用户。
- 主脑可以直接执行正常合并；代码修复、冲突解决及必要的整体验证交给新 worker。
- Worker 对工单验收负责，主脑对集成和最终目标收口负责，保留按需复核权。
- 小工具自动观测上下文并执行标准 worker 交接；异常交给主脑决策。
- 第一版只支持 Pi 和 OpenCode。
- 两种运行时都必须显式配置 `provider`、`model`、`thinking`，不得使用未确认的默认模型或静默替换配置。
- 确认最大并发数；不设置任务时间预算、费用预算或固定批次超时。
- 第一版只处理 worker 交接，不建设主脑交接、主脑恢复或无人值守的全局故障恢复。

“完整初始工单集”是启动条件，不意味着执行中工单集合不可改变。

### 1.2 简化的衡量标准

1. 主脑不必服从与任务正确性无关的操作仪式。
2. 主脑不必记住各运行时的按键、中断、投递和上下文读取细节。
3. 工具不理解工单依赖、不决定派什么工单、不替主脑决定重试或集成。
4. 同一事实尽量只保存一次；业务交付与终端空闲有明确区别。
5. 文档和接口足够小，能够按实际需要逐步扩展。

## 2. 当前实现与 Herdr 调研依据

### 2.1 当前项目的主要约束

| 现状 | 来源 | 重建处理 |
| --- | --- | --- |
| 四轮依次选择运行配置 | `SKILL.md:16–21` | 一次确认，已有完整配置时只校验 |
| 预先固定完整批次，改变计划需再确认 | `SKILL.md:23–28` | 授权范围内由主脑动态排程 |
| 等整批结束后才处理集成 | `SKILL.md:41–47` | 等任一待处理事项，逐项推进 |
| 禁止主脑二次验收 | `SKILL.md:42` | 默认信任交付，保留按需复核 |
| 常规失败也要求用户选择处置 | `SKILL.md:44` | 主脑自主判断，必要时新派 worker |
| 主脑直接修复合并冲突 | `SKILL.md:46` | 冲突修复交给新 worker |
| 旧 claimed 尝试默认销毁 | `bin/dispatcher.py:723–794` | 不沿用默认销毁政策 |
| completed 早于实际合并 | `bin/dispatcher.py:1300–1326` | 分开记录交付与集成 |
| 运行时适配混入大执行器 | `bin/dispatcher.py`、`bin/get_context.py` | 提炼 Pi／OpenCode 适配边界 |

以上行号对应调研时版本，仅用于追溯旧设计。

### 2.2 已确认的 Herdr 能力与限制

本机调研基线为 Herdr 客户端／服务端 0.8.2、协议 20，Pi 0.85.1、OpenCode 1.18.30；Pi／OpenCode 官方集成显示 current。官网当时标注 0.9.0，因此以 0.8.2 固定版本资料核对本机能力。

- Herdr 原生支持布局创建、agent 启动就绪、prompt 投递、服务端事件驱动等待、多 pane 状态订阅和用户通知。
- 现有执行器已经使用 `agent prompt --wait` 和 `agent wait`，不能把重建收益描述为第一次引入原生等待。
- `idle/done` 是生命周期信号，不等于工单验收通过；`blocked` 也可能是运行错误，不仅是权限问题。
- `prompt --wait` 不提供独立业务任务的完成关联；工作中再次投递可能被旧活动的结束满足等待。
- Herdr 没有已确认的通用持久 agent 邮箱或 exactly-once 交付协议。通知也不能充当可靠结果存储。
- 原生 worktree 创建会关联 workspace；现有项目使用 Git worktree 加 tab。二者 UI 拓扑不同，不应机械替换。
- Herdr live handoff 保活终端进程；agent resume 恢复原对话；本项目的 worker handoff 用文档启动新对话。这三者不能互相替代。
- Herdr 没有统一的上下文用量 API，需要运行时适配。
- 当前 pane 未返回 `agent_session`，说明官方集成已安装不等于所有会话都具有可用恢复引用。

调研做了源码、官方资料、本机帮助和只读接口检查；尚未进行新架构的真实启动、配置生效、自动交接或故障恢复实验。

## 3. 职责边界

领域定义见根目录 `CONTEXT.md`。以下是执行职责，不扩展词汇表为实现说明。

| 参与者 | 职责 |
| --- | --- |
| 用户 | 确认目标、范围、运行配置和并发上限；决定无法推断的需求取舍及授权变更 |
| 主脑 | 阅读完整输入，理解依赖，动态派发，调整工单，处理常规失败，按需复核，正常合并，组织修复与验证，判断整体完成 |
| Worker | 完成单个工单，执行验收，提交结果与验证证据；需要换会话时生成 handoff；完成后结束职责 |
| 小工具 | 创建与登记资源、可靠启动和投递、观测上下文、标准交接、结果与异常留存、等待待处理事项、按指令清理 |
| Herdr | 提供终端、agent 控制、生命周期观测及事件等待能力 |

主脑可以阅读代码、检查结果、运行检查以支持判断；具体实施和修复由 worker 承担。工具只做结构与资源一致性检查，不执行质量评审。

## 4. 主脑工作流

### 4.1 建立执行目标

1. 确认运行在 Herdr 环境中，发现实际 CLI 和官方集成能力。
2. 定位并阅读 spec／计划与完整初始工单集。默认目录兼容 `.scratch/<slug>/spec.md` 和 `issues/*.md`，也接受显式路径。
3. 理解显式与语义依赖，识别影响实施方向的未决需求；不要求生成固定批次 JSON。
4. 一次性确认目标、范围、worker 运行配置和最大并发数。已明确的信息直接沿用，只询问缺失或矛盾之处。
5. 建立简洁执行记录，开始派发满足条件的工单。

工具不解析整套 Markdown 依赖图，不要求特定文件名、编号正则或标题结构。主脑为每项任务分配稳定标识，并提供内容、引用、验收要求和明确基线。

### 4.2 动态执行循环

```text
观察工单与已集成成果
  → 在并发上限内派发当前可执行工单
  → 有管理工作则继续处理，否则等待任一待处理事项
  → 检查交付或异常
  → 正常集成／派修复工单／处置失败／询问必要的需求决策
  → 更新记录，重新判断下一步
```

依赖后续工作必须以所需成果已进入目标分支为前提，不能只看 worker 已交付。可使用批次作为某次安排，但批次不是唯一执行模式，也没有全局批次屏障。

主脑可以新增调查、修复、补测和集成工单，可以拆分过大的工单。修改应保留简要理由及与原目标的关系；避免把实施中新发现的必要工作误判为必须重新授权的需求扩张。

### 4.3 整体收口

主脑对照 spec／计划检查目标覆盖、集成结果及遗留问题。跨模块行为需要组合验证时，派 worker 执行；已有证据充分时复用证据，不强制固定的最终验收角色。

只有整体目标满足才报告完成。最终报告包含目标完成情况、主要集成结果、验证摘要、未解决事项及保留资源位置。

## 5. 运行配置

每次执行确认默认配置：`kind`、`provider`、`model`、`thinking`、`max_workers`。每个 worker 保存其实际使用的已确认配置，交接后的新会话必须保持一致。

- `kind` 仅允许 `pi` 或 `opencode`。
- 两者均要求用户明确选择 provider、model、thinking，不依赖运行时或项目中的默认模型。
- 目录查询只辅助选择和校验，不规定固定问答轮数，不悄悄切换 provider 或模型。
- 校验所选 provider／model 是否存在，并校验该模型与运行时是否能表达指定 thinking。不能只用一张全局枚举表就认定所有组合可用。
- 无法表达或确认生效的配置应在派发前报告，由用户决定如何调整，不自动降级。
- Pi 使用其支持的显式参数。OpenCode 适配器将三字段映射到支持的模型标识与推理配置；使用底层配置机制不等于允许默认模型。
- 本机 OpenCode 根 TUI 未提供 `--variant`；不能直接照搬 `run --variant`。优先验证通过新 pane 环境注入 `OPENCODE_CONFIG_CONTENT` 等受支持方式，避免改写业务仓库的 `opencode.json`。
- 不为设置模型而覆盖整个权限配置。交互阻塞由工具上报，主脑在已有授权和运行时能力范围内处理。
- 无任务时间、费用预算或最低运行时长。启动、命令响应等协议超时只用于识别操作失败，不能被当成工单执行时限；一次等待超时也不能推导工单失败。

并发额度按活跃 worker 计，交接前后的会话属于同一个 worker。替换会话前必须确认旧会话已停止业务执行，避免借交接突破并发限制。已交付、已停止执行的会话保留现场不占执行槽。

## 6. 最小工具边界

以下是接口语义草案，具体命令拼写可在实现时统一，不作为新增框架的理由。

| 操作 | 主要输入 | 结果 |
| --- | --- | --- |
| `start` | 工单标识、任务材料、配置、仓库、明确 base、管理记录位置 | worker 标识、分支、worktree、Herdr 定位与启动结果 |
| `status` | 当前执行或 worker 标识 | 当前执行事实、交接进度、交付／异常、资源位置 |
| `wait` | 当前执行标识、已处理位置 | 任一尚未处理的交付或异常；已有事项立即返回 |
| `ack` | 待处理事项标识 | 标记该事项已被主脑处理，不改变工单质量或集成结论 |
| `stop` | worker 标识 | 停止业务执行及自动交接，保留现场 |
| `cleanup` | worker 标识、明确清理决定 | 对已停止且符合清理条件的登记资源进行清理 |

按需提供主动交接入口，复用同一标准交接过程；不再额外设计另一套人工续接协议。

### 6.1 后台组织

建议每个活跃 worker 使用轻量生命周期监督进程，不创建全局调度服务。监督进程管理该 worker 的 Herdr 会话、上下文采样和交接；主脑离开当前工具调用时，它仍可继续工作。

共享等待层负责汇总待处理事项，可复用 Herdr 等待或订阅能力。后台启动和日志输出应由工具封装，主脑不必拼装后台 shell 命令或持有数小时的前台批次调用。

监督进程不自动领取新工单，不决定业务重试，不推进目标分支。监督进程本身意外退出时，`status/wait` 应能暴露监督缺失；第一版不自动重建监督或接管失联执行。

### 6.2 最小持久事实

每个 worker 保存必要字段即可：工单标识、执行标识、配置、base、branch、worktree、Herdr 定位、会话序号、上下文引用、监督进程身份、交接材料路径、交付结果和待处理异常。

运行记录放在目标仓库关联的管理目录中，例如 Git common dir 下的 `herdr-plan-manager/`。具体存储格式保持简单，原子写入，单个 worker 的生命周期状态只有一个负责写入的监督者。

每条交付或异常有稳定事项标识，主脑确认处理后记录 acknowledgement。Herdr 事件用于触发检查，持久结果用于避免漏报与重复处理；不宣称 exactly-once，不建设通用事件总线。

执行状态仅描述启动、运行、交接、交付、失败、待决策和停止等生命周期事实。工单调整、集成 SHA 和目标完成情况由主脑维护在执行记录中，不要求工具维护完整业务状态机。Acknowledgement 不等于已集成。

## 7. Worker 合同与交付

启动包必须包含：

- 单一工单的目标、范围、验收要求和必要依赖说明；
- 可访问的 spec／计划及参考材料；
- 工作目录、分支、base 与结果输出位置；
- 已确认运行配置、交接要求和遇到阻塞时的报告方式。

不能假定主 checkout 中被忽略或未提交的 spec 会自动出现在 worktree 中。任务材料应使用明确可访问路径或受控快照，记录来源；worker 不修改主脑维护的计划和其他工单文件。

Worker 完成后提交简短结构化结果：

- 工单和 worker 标识，以及 `delivered`、`failed` 或 `needs-decision` 声明；
- 完成摘要、验收覆盖和实际执行的验证及结果；
- 代码成果的 branch／HEAD，或调查与验证任务的产物位置；
- 遗留问题、未完成项和需要主脑判断的事项。

代码成果应提交并说明未提交内容；调查或验证工单不强制制造空提交。具体提交风格遵循目标仓库规范，不强加统一前缀。

工具验证身份、结果可读性、路径与分支一致性等协议事实。主脑默认利用 worker 的验收结果，不重复全部工作；发现疑点可以要求补充证据或派新 worker 处理。

终端空闲而缺少有效结果时，可以执行一次明确的结果补报流程；仍未取得有效结果则上报协议异常，不无限发送“继续”，也不伪造成功。

## 8. 上下文观测与标准交接

### 8.1 触发

初版沿用可配置默认值：观测到上下文达到 300K tokens，或窗口占用达到 80%，触发交接；主脑也可主动触发。300K 是经验性运行策略，不是模型能力退化的统一科学界限。

用量由 Pi／OpenCode 适配器读取，优先使用稳定、可验证的原生信息；需要保留数据库或会话文件适配时将其隔离。区分当前上下文与累计消耗、最近有效调用与陈旧样本。无法观测不能当作零用量，应形成可见异常。

### 8.2 标准过程

1. 确认当前会话身份及仍需交接，停止业务投递与旧等待。
2. 使用对应运行时支持的方式暂停业务执行，确认可以接收交接指令。
3. 明确要求使用 handoff skill，将目标、已完成工作、决定、验证、分支／提交、未提交内容及下一步写入指定文档。
4. 确认文档已生成且可读；必要时做一次结构性补正，不以字数阈值代替交接充分性。
5. 在同一 worktree、同一 branch 下启动新对话，传递原工单合同及 handoff 路径，保持已确认配置。
6. 确认新会话启动并成功接收续接指令后，结束旧会话，继续监督新会话。

两次会话不能同时修改同一 worktree。旧会话生成交接文档后应停止业务工作；新会话启动失败时保留材料与现场，交由主脑处置。

交接文档存入耐久管理目录。若 handoff skill 原流程先写 OS 临时目录，工具应在替换会话前保存耐久副本。不能假定 Pi 与 OpenCode 都支持字面 `/handoff`；适配器应验证可用 skill 调用方式。

交接成功不算新工单、不算业务重试，不要求主脑确认。每次交接递增会话序号，采样、等待与异常事件都关联该序号，避免旧会话事件触发新会话的重复交接。

## 9. 成果集成与修复

主脑从目标分支串行执行正常合并，具体 Git 策略遵循目标仓库规范，不强制固定 ff／no-ff 或 squash 政策。合并前确认目标工作区适合操作，合并后记录工单交付与实际集成 SHA 的对应关系。

遇到冲突时，主脑不修改冲突文件。建议流程：

1. 保存 incoming branch／SHA、合并前目标 SHA、冲突摘要及相关工单要求。
2. 对本次由主脑发起的合并，确认前置工作区条件后使用可控的 Git 中止流程恢复目标；中止失败或存在无法区分的用户工作时，保留现场并报告，不强行 reset。
3. 派新修复 worker，从明确目标基线建立隔离的集成分支，复现合并并解决冲突，验证兼容需求。
4. 主脑审阅交付摘要并集成修复分支；若目标已变化，重新判断兼容性，必要时另派修复工单。

无文本冲突但出现组合行为错误时，同样派新修复 worker。影响相关依赖的已知问题解决前，不继续解锁依赖工单。

在修复期间，主脑可以继续安排无关工作；工具不决定哪些任务应暂停。主脑可以选择短暂稳定目标基线以减少重复冲突。

## 10. 异常与清理

- 启动或投递出现可明确判断的瞬态错误时，工具做有限、可观测的机械重试；投递是否已接受不确定时先查状态，不盲目重发业务任务。
- Worker 业务失败、需求疑问、阻塞 UI、交接失败或持续观测失败，形成待处理事项，由主脑判断。
- 主脑可在授权范围内自主重试、换 worker、派调查或修复工单；重复无进展时应改变策略或报告阻塞，不能无限重复同一尝试。
- 交付后停止自动交接，保留结果与 worktree，等待主脑集成或处置。
- 正常结束且确认无未保存工作时可以关闭会话；失败与异常保留可用现场。
- 集成后的清理由主脑明确触发。工具确认资源归属、无活动写入及无需要保留的未提交内容后再删除 worktree；分支删除遵循仓库习惯。
- 不沿用 stale claimed 自动删除分支／worktree 的政策。不关闭未登记终端，不以清理为由丢弃未提交成果。

持久记录用于当前执行的可靠结果收集与定位，不代表第一版承诺主脑交接、崩溃恢复或自动接管能力。

## 11. 实施路线

### 阶段一：验证最小 Herdr／运行时链路

- 用一次性仓库分别验证 Pi 和 OpenCode 的显式 provider／model／thinking 配置，检查实际生效值。
- 验证启动就绪、prompt 投递、空闲与 blocked 语义，以及正确的中断方式。
- 验证两种运行时能调用 handoff skill，新会话确实读取文档并保持工作目录和配置。
- 验证后台监督与等待接口能在实际主脑工具环境中使用。

产出：可重复的冒烟步骤和已确认的适配策略。历史兼容补丁仅在复现或存在明确版本依据时保留。

### 阶段二：建立单 worker 生命周期工具

实现启动、状态、停止、结果协议、资源登记及有限投递补正。先让单个 worker 从启动走到可处理交付，再加入自动交接与异常保存。

建议复用并审查现有 `get_context.py`、`pi_context.mjs`、handoff 及启动处理逻辑。重点修正会话身份、停止确认、配置污染和临时交接文件等风险，不整段搬运旧执行循环。

### 阶段三：实现多 worker 等待与主脑执行方法

实现并发额度、待处理事项、acknowledgement 和 wait-any；后台仍不排程。编写精简 `SKILL.md`、worker 合同和按需加载的操作参考，接入主脑动态调度、正常合并与新 worker 修复流程。

### 阶段四：端到端验收并迁移

覆盖下节场景后，将 skill 名称、说明和调用入口迁至 `herdr-plan-manager`。仓库目录迁移在实际实施时统一处理，更新引用，不在只写方案阶段移动当前项目。

新工具验证通过后删除旧固定批次入口、Codex 适配、严格工单解析器及过时 schema／测试。旧运行记录不自动解释为新状态，也不自动接管或清理旧 worker。

不提供兼容旧固定批次接口的复杂转换层；迁移说明解释新操作与职责即可。

## 12. 验收场景

1. **统一显式配置**：Pi／OpenCode 均按确认的 provider、model、thinking 启动；不支持的组合在启动前可见失败，无默认模型回退。
2. **动态推进**：A 与 B 并行，A 先交付；主脑合并 A 后即可启动仅依赖 A 的 C，无需等 B。
3. **自动交接**：用可控低阈值验证同工单跨会话继续，分支／worktree／配置保持一致，旧会话不再写入；正常交接不唤起主脑决策。
4. **交接竞态与失败**：陈旧采样不触发新会话交接；文档生成或替换启动失败能上报，现场不丢失。
5. **可靠待处理事项**：结果先于 wait 写入仍能被发现；ack 后不重复返回；Herdr 通知遗漏不影响结果可见性。
6. **完成语义**：终端 idle 而无交付结果不能算完成；已交付但未集成不能解锁依赖。
7. **冲突由新 worker 解决**：A、B 冲突时，主脑仅执行管理动作，新 worker 完成隔离修复与验证，随后由主脑集成。
8. **整体目标收口**：工单均交付但组合验证失败时，主脑新增修复工单，不能报告整体完成。
9. **安全清理现场**：失败、未集成、未提交内容及归属不明资源不会被自动强制删除。
10. **材料可见性**：spec／工单只存在于主 checkout 本地时，worker 仍能读取明确提供的材料。
11. **授权与并发**：主脑自主调整工单，工具不自行领新工单；交接不会造成两个业务会话并写同一 worktree 或突破执行额度。
12. **非代码工单**：调查、补测结果可以交付，不要求制造无意义提交。

测试聚焦生命周期、竞态、结果语义和跨运行时集成。文件格式等低风险细节不扩展成庞大镜像测试；真实运行时冒烟与确定性故障模拟互补。

## 13. 明确删除与保留

**删除或不建设：** 固定四轮问答、全量固定批次确认、批次屏障、任务时长／费用预算、Codex、工具级 DAG 排程、禁止主脑复核、主脑亲自修复、stale 自动销毁、主脑恢复系统。

**保留并简化：** 独立 worktree、显式运行配置、可靠启动投递、上下文观测、标准 worker 交接、原子结果记录、资源归属、wait-any、成果交付与集成的区分、按决定清理。

最终形态应是一份主脑可以灵活运用的执行方法，加一组替主脑消除机械负担的小工具。
